# The algebra tools on the real public games (level 1)

Date: 2026-10-12. Scripts:
- `scripts/algebra_on_games.py` (click algebra, movement): output in `runs/algebra_on_games/results.json`;
- `scripts/bfs_on_games.py` (bfs_plan, zm_solve, visible-Markov check): output in `bfs_zm.json`;
- `scripts/summarize_algebra_on_games.py`: the summary table.

**What this measures.** The experiments use engine access no agent has: unlimited fresh instances and deep-copied game states. They measure two things:
1. how often real level-1 mechanics fall inside each tool's model class;
2. whether the tools act correctly on the real engine when they are given the right inputs.

They do **not** measure agent performance or score. The model still has to discover the mechanic and encode it. The 25 games are public, so the class frequencies below may not hold on the hidden set.

**Step counters.** Most games have a step bar that changes with every action. Its pixels are excluded before any comparison:
- (i) pixels that change under k = 1..8 clicks on empty background;
- (ii) with ≥ 3 buttons, pixels that every button's k-click sequence changes;
- (iii) with < 3 buttons, the 3-pixel edge band.

The first version used a frequency-based HUD mask. It reported 0% superposition on ft09, which comes out as an exact XOR game once the bar's second pixel is masked. The comparisons are therefore conservative only after this fix.

## 1. Click mechanics: which model class holds? (15 games with ACTION6)
Effective buttons are clicks at component centres that change more than 4 non-counter pixels. Pair and triple tests are run from the start state.

| Class (definition) | Games | Tool whose assumptions hold |
|---|---|---|
| **XOR toggle**: superposition, commutation and involution hold on every tested pair and button | ft09, cn04 | `gf2_solve` |
| **Partial XOR**: commutation 100%, superposition on 57–65% of pairs | bp35, s5i5 | `fit_boolean` (§2) |
| **Inverse buttons**: two buttons cancel each other | lp85, vc33 | `fit_guarded` / `zm_solve` |
| **Commuting, other** | cd82, dc22 | none of the GF(2) class |
| **Order-dependent / last click wins**: a selection or highlight follows the last click, so commutation fails | r11l, su15, sb26, lf52 | none |
| **No effective component-centre click at level 1** | ar25, ka59, m0r0, sc25, sk48, sp80, tn36 | n/a |

**GF(2) planning on the engine.** Targets are generated by real random click subsets. `gf2_solve` is run on the single-click effect matrix, and the plan is replayed on a fresh instance.
- **XOR class:** 35/35 plans exact and 0 false plans, at nullity 0–2.
- **Partial XOR:** 31 exact, 14 rejected (`None`, i.e. "the toggle model is wrong") and 0 false. bp35 has 28 buttons with nullity 21, so many buttons duplicate each other's effects, and its 14 non-trivial plans were all exact.
- **Order-dependent class:** r11l produced **1 false plan in 25**, a confident plan that fails on the engine. That is exactly the failure that math_contract row 6 guards against ("commutation and repeat-activation must be validated first"). The model-facing `TOOL_DOC` did not state those prerequisites. **Fixed** in commit 1ec396b (one clause). The algebra notebook was rebuilt (only the embedded tools line differs), and the rerun path was re-verified (`RERUN OK: True`, clause present in the system prompt).
- Many "successful" plans outside the XOR class are coincidental. In last-click games every reachable target is a single-click state, so any model reaches it. Plan success there is **not** evidence for the toggle model; only the pair tests decide the class.

## 2. Polynomial vs XOR: held-out prediction (`fit_boolean`, degree ≤ 2)
**Method.**
1. For up to 12 random button triples, play all 8 subsets of the triple.
2. For each touched pixel, fit the changed-indicator on the 7 subsets other than {a,b,c} with `fit_boolean` (degree ≤ 2, ≤ 4 terms).
3. Predict {a,b,c}, which is never observed, and compare with the engine.

The reference predictor is XOR superposition of the three singles.

| Game | Triples | Frames exact (deg ≤ 2) | Pixel accuracy deg ≤ 2 | Pixel accuracy XOR |
|---|---|---|---|---|
| ft09 | 12 | 12/12 | 1.000 | 1.000 |
| bp35 | 12 | 11/12 | 0.993 | 0.753 |
| s5i5 | 12 | 10/12 | 0.853 | 0.367 |
| cn04 | 1 | 0/1 (tool: no fit) | 0.000 | 1.000 |
| r11l | 12 | 2/12 | 0.555 | 0.272 |
| lf52 | 12 | 0/12 | 0.478 | 0.391 |
| sb26 | 4 | 0/4 | 0.667 | 0.333 |
| su15 | 1 | 0/1 | 0.500 | 0.200 |

**Reading.**
- In bp35 and s5i5 the low-degree multilinear model predicts unseen combinations that the XOR model gets wrong (99% vs 75% and 85% vs 37% of pixels). This is real-game support for the polynomial extension over GF(2).
- In cn04, three buttons toggle the same pixels. That is 3-way parity, which needs a degree-3 term over the reals. `fit_boolean` correctly answers "no rule with ≤ 4 terms of degree ≤ 2" rather than guessing, and XOR is exact.
- The two classes are therefore complementary. The cheap pair superposition test selects between them: 100% superposition means use XOR, otherwise use the polynomial fit.
- In order-dependent games both fail, as they should.

## 3. Movement: guarded affine (`fit_guarded`) and wrap-around (`zm_solve`)
Each direction key is pressed k = 1..12 times on fresh instances. The rigid mover is tracked by shape signature, and `fit_guarded` is fitted per coordinate.
- **Steady motion:** constant step on ≥ 2 moves, then held at a wall (22 tracks) or not yet at a wall (3), across 11 games. `fit_guarded` is exact on **25/25**. In all 22 walled tracks the reported `guard_between` interval contains the observed stop.
- **Wrap-around** (tr87 left/right; re86): **3 tracks**. `fit_guarded` correctly returns None (no single guard explains them). tr87's keys form genuine cyclic groups (keys 1/2: Z₇, keys 3/4: Z₅). `zm_solve` on the Z_m model picked the cheapest presses for every residue: 20/20 replays matched the target frame, using the inverse key when it is cheaper (`cost == min(r, m−r)` asserted).
- **Single jumps** (13 tracks): one change, then constant. The slope is not identifiable from one move. The tool's reply is still exact (a step at a wall located in (0,1)). The model must not read it as a speed.
- **Not testable:** 17 directions do nothing at the start state; 5 have no rigid mover (shape changes); 2 are irregular.

## 4. Planning ceiling (`bfs_plan` with the engine as the simulator)
Actions are the available keys plus effective component-centre clicks (≤ 30). The key is the interior frame, as a model-written simulator would use. Limits: 120 s or 20,000 nodes. Each plan is replayed on a fresh instance.

## 5. What this means for the competition
- **What the tools do once the model is right.** When the right model is supplied, every returned plan completes the level. The plans are far shorter than the human baselines (median 0.34 of the level-1 baseline). This confirms the measured loss decomposition (50.9 points lost to levels not completed vs 2.6 to inefficiency). The binding step is **identifying the mechanic and encoding it**, which no tool here does for the model.
- **Coverage.** Exact algebraic classes cover a minority of click mechanics: XOR 2/15, polynomial a further 2/15, inverse/cyclic 2/15 plus tr87's keys. Steady-plus-wall motion is common, 25 tracks across 11 games, but it is also easy for a model to handle without a tool.
- **Two failure modes seen on real games.**
  - (a) A toggle solver applied outside its class gives a confident wrong plan. Fixed in the prompt text, but the model still has to run the checks.
  - (b) `bfs_plan` reports "exhausted" (unreachable) for goals humans reach when the model's action set or state key is incomplete (§4).

  Both are documented caveats, and both are now confirmed on the actual games.
- **Effect on the Oct 13 submission.** The submission keeps the tools, with the one-clause documentation fix. No score claim is made from this analysis. Whether the tools change score is measured only by the leaderboard and, later, by token-matched ablations.
